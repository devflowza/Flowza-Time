### A.3 Country launch gates (compliance checklist per market)

Each gate must be green before the first tenant in that country is created. Items marked *(law)* need counsel
sign-off; items marked *(product)* are FlowZa deliverables from §A.2.

- **Oman (pilot, Phase 1)**
  - *(law)* Confirm RD 6/2022 Arts 5, 11, 15, 19, 20, 23 and MD 34/2024 Arts 27, 30–33, 37–40 against the Gazette; confirm
    that punch data from biometric devices (without templates) is *not* itself Art 5 data — if it is, every Omani tenant
    needs an MTCIT permit before go-live.
  - *(law)* Transfer risk assessment (Reg Art 39) naming the chosen AWS region, transit path and Supabase as sub-processor.
  - *(product)* `region_cell` immutable and shown in settings; DPO fields; `employee_consents` with `CROSS_BORDER_TRANSFER`
    and `ATTENDANCE_PROCESSING` purposes and the signed artefact; `security_incidents` table + notification runbook;
    retention defaults with reasons; `ramadan_reduced_hours` flag; bilingual consent template.
  - *(product)* Signed DPA with sub-processor list; privacy notice EN/AR.
- **UAE (Phase 4)**
  - *(law)* Executive Regulations status (Cabinet Decision 111/2023 vs pending); breach deadline; onshore vs DIFC/ADGM.
  - *(product)* `jurisdiction_regime` value per tenant; DPIA template (Art 9, systematic monitoring); DPO fields;
    UAE preset (8/48, Ramadan −2 h **all** staff, night 22:00–04:00, OT cap 2 h); retention ≥2 y post-termination.
- **KSA (Phase 4)**
  - *(law)* SDAIA controller registration for tenants; SCC module for FlowZa as processor; mandatory TRA for continuous
    sensitive transfers; base hours (45 vs 48) and rest days (1 vs 2) confirmed.
  - *(product)* Dedicated cell decision (Frankfurt/Mumbai project vs self-hosted); Arabic privacy notice mandatory;
    KSA preset with weekly-criterion OT and "all holiday hours = OT"; 12 h presence flag; annual OT cap alarm.
- **Qatar (Later)**
  - *(law)* NCGAA permit rules for biometric-derived data; QFC regime; breach SLA.
  - *(product)* `QA` / `QA_QFC` regimes; preset 8/48, Ramadan 6/36, night 21:00–03:00, Friday 150 %.
- **Kuwait (Later)**
  - *(law)* Confirm no omnibus statute applies to a SaaS processor; CITRA scope.
  - *(product)* Oman-grade baseline anyway; Overtime Register report (Art 66); caps 2 h/day, 3 d/wk, 90 d/yr, 180 h/yr.
- **Bahrain (Later)**
  - *(law)* Confirm tenant holds PDPA Art 15 prior authorisation + DPIA (Orders 43/44 of 2022) before biometric devices go
    live; confirm hosting country is on the Order 42/2022 adequacy list (Frankfurt/EU is; Mumbai is to be checked).
  - *(product)* `data_protection_authorisations` record gates biometric-capability devices; preset 8/48, 60 h ceiling,
    night 19:00–07:00, Friday 150 %.

### D.2 Where the judges disagreed with the blueprint — and the final rationale

| Decision | Blueprint / ADR | Judges' & proposals' position | Final position and rationale |
|---|---|---|---|
| **Queue transport** | ADR-006: custom `jobs.queue` (`FOR UPDATE SKIP LOCKED`, fairness in `jobs.dequeue`, reaper, archive) behind a `JobQueue` port | All three judges preferred **pgmq** as transport + a pg_cron/worker-driven **SQL admission dispatcher** for fairness (deletes ~300 lines of bespoke reaper/archive/backoff SQL; dashboard visibility; `set_vt` leases). Proposals 12 and 13 kept the custom queue (13 with weighted deficit round-robin lanes + BullMQ offload at stage 3). | **Keep the custom queue for v1** (ADR-006 review note). Fairness/throttling must be written either way; plain Postgres in CI has no pgmq; transactional enqueue is preserved in both. The judges' point is accepted as the *trigger*: when queue throughput or write amplification is measurable, swap the transport behind the port (pgmq first, Redis/BullMQ second). Adopt now from the judges: `jobs.heartbeat`, lease-token CAS, `queue_fairness.sql`, oldest-pending-per-org alert, inline dispatch for manual jobs. |
| **API host** | ADR-001: Node Hono container + Node worker | Proposal 11 wanted the API as one Edge Function (`packages/api-core` with Deno/Node adapters). All three judges and proposals 12/13 rejected Edge as the production host (HTTP 546 cliff, 256 MB, dual-runtime drift, HTTP-only ADMS devices need a container anyway). | **Node container confirmed.** Keep the Hono app runtime-agnostic so an Edge adapter remains a later option for thin endpoints; API and worker ship as one image with two entrypoints. |
| **Credential storage** | ADR-003: app-side AES-256-GCM envelope, KEK outside DB | Proposal 11 proposed Supabase **Vault**; judges unanimously called Vault a security downgrade (`vault.decrypted_secrets` readable by anyone with `postgres`/dashboard access; throughput at 100k+ secrets unverified). Proposal 13 wanted KMS-wrapped per-org DEKs. | **App-side envelope confirmed.** Vault permitted only for platform secrets SQL itself must read (webhook HMAC if webhooks ever move to Edge). Adopt `credential_rotations`, test-connection-before-commit, per-cell KEKs; KMS `MasterKeyProvider` when enterprise/KSA requires it. |
| **DB-driven permissions vs JWT claims** | ADR-002/007: nothing authorisation-relevant in JWT | All judges and proposals agreed (immediate revocation). CISO added: bind platform admins to grants on *all* customer tables; forbid non-LOCAL `SET ROLE`; `flowza_api` zero grants. | **Confirmed**, with the hardening items folded into D3/D4/D15. |
| **"No business logic in triggers"** | Blueprint §C: only integrity/immutability triggers | Critic (A5) argued invariants (immutability, period lock, tenant FK) must live in the DB, not only in services. Judges praised exactly those triggers. | **Refined rule:** *workflows* in the service layer; *invariants* (REVOKE on raw/audit, `protect_*` triggers, period-lock guard, composite tenant FKs) in the database. Already implemented in `1100`/`1200`; document the split in ADR-005. |
| **Fairness in SQL** | Fairness in `jobs.dequeue()` (SQL) | CTO judge noted this is business logic in the DB, contrary to the brief. | Accepted as **infrastructure code**, not business logic: it must be atomic with `SKIP LOCKED`; covered by pgTAP; documented. |
| **Realtime publish path** | Blueprint §C: API/worker publish via REST with service key | Judges preferred publishing from SQL (`realtime.send`) inside the state-changing transaction (ordering, no service key in worker). | **Open (F-4):** adopt `realtime.send` from the service layer once availability is asserted in CI for both local image and hosted project; keep REST publisher as fallback. Either way the service key never touches data paths. |
| **Local test stack** | Plain Postgres + shim for fast loop; full Supabase stack nightly | Judges: CLI stack should be primary/gating because the design leans on Supabase-only primitives. | **Both:** plain Postgres for unit/RLS speed on every PR; **full CLI stack gates merges to `main`** (not only nightly) for Realtime/Storage/Auth paths. |
